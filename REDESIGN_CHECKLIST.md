# Checklist do Redesign

Princípio central: **profissional na superfície. Benjamin nos detalhes.**

O portfólio deve continuar funcionando como uma apresentação profissional mesmo para quem não reconhecer nenhuma referência pessoal. As referências devem acrescentar uma segunda camada, nunca prejudicar a leitura principal.

## 0. Decisões antes de começar

- [x] Escolher o universo de anime: Attack on Titan.
- [ ] Definir a música inicial e os metadados do player.
- [ ] Confirmar as imagens/assets permitidos para a intervenção de The Last of Us.
- [x] Preparar a estrutura para case studies nesta versão; construir as páginas detalhadas posteriormente.
- [ ] Confirmar dados de formação acadêmica para o capítulo Aprendizado.
- [ ] Definir quais certificações terão links para credenciais.
- [ ] Confirmar a estratégia de idioma: conteúdo principal em português e labels curtos em inglês.
- [ ] Decidir se a página 404 temática entra no mesmo escopo do redesign.

## 1. Preparação e arquitetura

- [x] Mapear o conteúdo atual que será preservado, reescrito, movido ou removido.
- [x] Definir a nova ordem da página:
  - [x] I — Introdução
  - [x] II — Sobre
  - [x] III — Experiência
  - [x] IV — Projetos Selecionados
  - [x] V — Ferramentas
  - [x] VI — Aprendizado
  - [x] VII — Contato
- [x] Separar interlúdios não numerados da navegação principal.
- [x] Definir âncoras, navegação e comportamento de scroll entre capítulos.
- [x] Definir a organização inicial dos projetos:
  - [x] Finova como projeto principal e primeiro candidato a case study.
  - [x] Doss Imobiliária como experiência profissional com destaque de impacto.
  - [x] Rego Barros como trabalho independente entregue.
  - [x] Ki-Dilicia como projeto em desenvolvimento.
- [ ] Remover a dependência de uma sequência repetitiva de cards sempre que houver uma solução editorial melhor.

## 2. Direção visual

- [x] Adotar estética editorial, cinematográfica, minimalista e profissional.
- [x] Usar fundo escuro profundo, superfícies discretas e contraste controlado.
- [x] Usar dourado queimado como accent principal, sem transformar a interface em uma paleta monocromática.
- [x] Definir e carregar a hierarquia tipográfica:
  - [x] Geist ou fallback equivalente para interface e texto.
  - [x] Cormorant Garamond para títulos editoriais e citações.
  - [x] Geist Mono ou fallback equivalente para labels, capítulos e metadados.
- [x] Usar bastante espaço negativo entre capítulos.
- [x] Manter raios, bordas, sombras e transições sutis e consistentes.
- [ ] Evitar gradientes chamativos, excesso de blur e decoração sem função.
- [x] Criar tokens centralizados para cores, tipografia, espaçamento, radius e motion.

## 3. Introdução / Hero

- [ ] Apresentar imediatamente Benjamin Montenegro.
- [ ] Comunicar claramente Full Stack Developer.
- [ ] Usar uma descrição curta sobre produtos digitais, interface, backend, arquitetura e cloud.
- [ ] Priorizar o nome como elemento visual principal.
- [ ] Incluir ações claras para projetos, currículo e contato.
- [ ] Exibir localização como metadado, sem transformar o Hero em autobiografia.
- [ ] Preservar espaço negativo e sensação de segurança visual.

## 4. Sobre

- [ ] Não repetir a apresentação do Hero.
- [ ] Abrir com uma frase autoral sobre entender problemas e fazê-los funcionar melhor.
- [ ] Usar um texto profissional curto, pessoal e em primeira pessoa quando natural.
- [ ] Separar fatos objetivos em metadados:
  - [ ] Focus
  - [ ] Location
  - [ ] Languages
  - [ ] Currently
- [ ] Manter o texto conciso e evitar linguagem corporativa genérica.

## 5. Experiência

- [ ] Apresentar contexto, atuação e impacto.
- [ ] Reestruturar a Doss Imobiliária como Full Stack Developer.
- [ ] Separar responsabilidades em itens objetivos.
- [ ] Dar destaque visual para resultados mensuráveis, especialmente leads e conversão.
- [ ] Avaliar a inclusão dos trabalhos freelance como Independent Work dentro do mesmo capítulo.
- [ ] Mostrar período, função e tecnologias como metadados.

## 6. Projetos Selecionados

- [ ] Apresentar projetos como trabalhos selecionados, não apenas como uma grade de cards.
- [ ] Para cada projeto, responder:
  - [ ] O que é?
  - [ ] Por que existe?
  - [ ] Qual foi o papel de Benjamin?
  - [ ] Qual foi a principal decisão ou ideia?
  - [ ] Com quais tecnologias foi construído?
- [ ] Usar metadados consistentes: Role, Built With, Core Idea e Case Study.
- [ ] Manter tecnologias presentes, mas sem deixá-las dominar a composição.
- [ ] Aproveitar a mitologia grega como parte natural da identidade dos projetos.
- [ ] Preparar a estrutura para cases futuros com: problema, decisões, arquitetura, interface, desafios e resultado.

## 7. Interlúdios e ritmo

- [ ] Inserir respiros entre blocos densos de conteúdo.
- [ ] Criar pelo menos um interlúdio tipográfico com citação literária.
- [ ] Usar serifada, espaço negativo e autoria discreta na citação.
- [ ] Avaliar seleção aleatória de citações sem comprometer acessibilidade ou estabilidade visual.
- [ ] Trabalhar o ritmo: conteúdo → silêncio → descoberta → conteúdo.

## 8. Camada pessoal

- [ ] Manter a personalidade como camada ambiental, sem seção de hobbies.
- [ ] The Last of Us: usar uma intervenção visual discreta de Ellie em scroll reveal.
- [ ] The Last of Us: usar a mariposa apenas como easter egg menor.
- [ ] Bloodborne: reservar referências para interface, tooltips, mensagens, estados secretos, console e/ou 404.
- [x] Attack on Titan: representar por símbolos e ideias, nunca apenas por personagem exposto.
- [ ] Arcane: usar movimento, rabiscos e imperfeições controladas com baixa frequência.
- [ ] Música: usar player próprio, pequeno e persistente, sem autoplay.
- [ ] Mitologia: manter Argos/Ariadne e outros nomes ligados à função dos produtos.
- [ ] Limitar os universos culturais ao conjunto definido; uma nova referência precisa substituir ou justificar sua entrada.

## 9. Ferramentas

- [ ] Organizar tecnologias por função, sem barras arbitrárias de proficiência.
- [ ] Separar Front-End, Back-End, Data e Cloud & DevOps.
- [ ] Revisar a lista real de tecnologias antes da implementação.
- [ ] Evitar uma parede de logos; privilegiar nomes, agrupamento e hierarquia.
- [ ] Usar o texto editorial: “Ferramentas mudam. Fundamentos permanecem.” ou uma versão equivalente.

## 10. Aprendizado

- [ ] Reunir formação acadêmica e certificações em um único capítulo.
- [ ] Apresentar o aprendizado como trajetória contínua.
- [ ] Mostrar educação com curso, instituição e período.
- [ ] Mostrar certificações com nome, emissor, ano e credencial quando houver.
- [ ] Evitar cards grandes e logos dominantes nesta seção.

## 11. Contato

- [ ] Encerrar com uma pergunta humana, como “Vamos construir alguma coisa?”.
- [ ] Comunicar abertura para oportunidades, projetos e conversas sobre tecnologia.
- [ ] Priorizar email, GitHub e LinkedIn.
- [ ] Manter formulário apenas se ele trouxer valor real além dos canais diretos.
- [ ] Evitar tom de chamada comercial.

## 12. Interações e motion

- [x] Implementar reveal de scroll com progressão suave.
- [ ] Usar parallax lento apenas onde houver ganho visual claro.
- [ ] Criar hover secrets raros e coerentes.
- [ ] Fazer interferências de Arcane aparecerem e desaparecerem sem quebrar layout.
- [ ] Garantir que nenhuma animação seja necessária para compreender o conteúdo.
- [x] Respeitar `prefers-reduced-motion`.
- [x] Garantir foco visível e navegação por teclado em todas as interações.

## 13. Responsividade e acessibilidade

- [ ] Validar desktop largo, desktop comum, tablet e mobile.
- [ ] Garantir que títulos editoriais não causem overflow.
- [ ] Manter leitura confortável em colunas estreitas.
- [ ] Garantir contraste suficiente nos labels mono e no accent dourado.
- [ ] Usar alt text em imagens relevantes.
- [ ] Não depender apenas de cor para estados ou significados.
- [ ] Manter links externos identificáveis e acessíveis.
- [ ] Testar o player de música em mobile sem ocupar espaço excessivo.

## 14. Verificação final

- [ ] Conferir que a leitura profissional funciona sem nenhuma referência pessoal.
- [ ] Conferir que as referências pessoais são discretas e não competem com o trabalho.
- [ ] Conferir que cada referência funciona mesmo para quem não a reconhece.
- [ ] Revisar todos os textos pela regra “se cabe em 8 palavras, não usar 30”.
- [ ] Verificar todos os links, currículo, GitHub, LinkedIn e projetos publicados.
- [ ] Validar estados de loading, erro, 404 e ausência de conteúdo.
- [ ] Testar tema, scroll, navegação, player e interações em mobile e desktop.
- [ ] Revisar performance de imagens, fontes, animações e scripts.
- [ ] Fazer uma passagem final de coerência visual e editorial.

## Critério de aprovação

O redesign está pronto quando o visitante consegue identificar rapidamente quem é Benjamin, o que ele constrói e como continuar explorando. A camada pessoal deve aparecer para quem presta atenção, mas nunca ser necessária para entender o portfólio.
